# error-api-时区 · started_at(+08:00) 时区处理不一致导致趋势/健康度错算

> 首次记录 2026-06-01 ｜ scope: api ｜ 状态: 已修复

## 现象

- 健康度趋势图（`/api/db/alarm-trend`、`/api/health-score`）每小时格大多显示 0 / 与实际告警对不上。
- 健康分偏高（新发生的 critical 告警没把分数压到应有水平）。

## 根因（一句话）

`alarm_records.started_at` 由 `alarmRepository.nowBeijing()` 写入，是**带显式 `+08:00` 偏移**的北京时间串（如 `2026-06-01T08:00:00.000+08:00`）。SQLite 的 `datetime()/julianday()/strftime()` 会**自动按该偏移归一到 UTC**。但多处代码误以为 started_at 是「无时区的北京裸时间」，于是：

1. **多减 8 小时**：`(julianday('now') - julianday(datetime(started_at,'-8 hours')))*24` —— started_at 已归一 UTC，再 `-8h` 使 `hours_ago` **多偏 8 小时**。新 critical 的 `recencyDecay` 从 1.0 掉到 0.667，impact 25→16.7，**健康分被高估约 8 分**。
2. **分桶键 UTC/北京错位**：SQL 用 `strftime(...,datetime(started_at))`（UTC 小时）或 `datetime(started_at,'-8h')`（UTC−8），而 JS 补桶用北京小时 → `Map.get` 永远 miss → **趋势图几乎全 0**。
3. **窗口边界时区错位**：`WHERE started_at >= datetime('now','-24 hours')` 拿「带 +08:00 的串」跟「UTC 串」做**字典序比较**，窗口被偏移/放宽约 8h。
4. **hours 参数未校验**：`'-${hours} hours'` 字符串拼接（`parseInt` 已消毒，非真注入，但负数/NaN/超大值会让 SQL 退化或越界补桶）。

## 修复

新增 `src/utils/time.ts`：
- `clampHours(h)` —— 收敛为 `[1,168]` 正整数，NaN/负/0 → 24。
- `beijingCutoffHours(h)` —— 返回「h 小时前」的 `+08:00` 串，专用于 `WHERE started_at >= ?`。

统一原则（**比较/计算用 UTC、展示用北京**）：
- `hours_ago` 直接 `(julianday('now') - julianday(started_at)) * 24`，**禁止再 `-8 hours`**。
- 北京小时桶用 `strftime('%H', started_at, '+8 hours')` / `strftime('%Y-%m-%dT%H:00', started_at, '+8 hours')`，JS 补桶以 `Date.now()+8h` 为基准，二者键完全一致。
- 时间窗用 `started_at >= beijingCutoffHours(h)`（同为 +08:00 串 → 字典序=时序、命中索引），**不要**把 started_at 跟 `datetime('now',...)`（UTC、异格式）比。

涉及文件：`src/server/healthScore.ts`(computeCurrentScore / queryHourlyTrend)、`src/db/alarmRepository.ts`(queryAlarmTrend / reconcileAlarmStates / queryAlarmLatencyPercentiles)。三个被测函数加了可选 `db` 参数（测试缝，向后兼容）。
