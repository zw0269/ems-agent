## §1 命名

### 文件命名
- **主流模式**: camelCase.ts（如 agentLoop.ts、statusStore.ts）
- **比例**: 100%
- **适用场景**: 所有 TypeScript 源文件

### 组件/类命名
- **主流模式**: PascalCase（如 AgentLoop、LLMClient、ToolRouter）
- **比例**: 100%
- **适用场景**: 所有类定义

### 函数/变量命名
- **主流模式**: camelCase（如 processAlarm、gatherSnapshot、buildSystemPrompt）
- **比例**: 100%
- **适用场景**: 函数、变量、参数

### 常量命名
- **主流模式**: UPPER_SNAKE_CASE（如 ALARM_PRIORITY、TOOLS_DEFINITION、KNOWLEDGE_PATH）
- **比例**: 100%
- **适用场景**: 模块级常量、配置常量

### 数据库字段命名
- **主流模式**: snake_case（如 alarm_id、created_at、input_tokens）
- **比例**: 100%
- **适用场景**: SQLite 表字段、列名

### 环境变量命名
- **主流模式**: UPPER_SNAKE_CASE（如 LLM_PROVIDER、EMS_BASE_URL、SMTP_HOST）
- **比例**: 100%
- **适用场景**: .env 文件中的所有变量

## §2 目录分层

### 主流模式: 按层分离（Layer-based）
- **结构**: config/ db/ gateway/ llm/ notifier/ runtime/ server/ tools/ types/ utils/
- **比例**: 100%
- **适用场景**: 整个项目
- **特点**: 
  - 每层职责清晰（数据库层、网关层、运行时层等）
  - 跨层依赖通过导入实现
  - 无 barrel exports（每个文件直接导入）

### 测试位置
- **主流模式**: 独立 tests/ 目录（与 src/ 平级）
- **比例**: 100%
- **适用场景**: 所有测试文件

## §3 状态管理

### 全局状态
- **主流模式**: 单例模式 + 内存存储
- **示例**:
  - `statusStore` (server/statusStore.ts): 全局状态对象，直接导出
  - `_db` (db/database.ts): 数据库连接单例，通过 getDb() 获取
- **适用场景**: 跨模块共享的运行时状态

### 会话状态
- **主流模式**: 类实例管理
- **示例**: SessionManager 类维护 Map<alarmId, timestamp>
- **适用场景**: 需要生命周期管理的状态

### 配置加载
- **主流模式**: 热加载（每次使用时重新读取文件）
- **示例**: KNOWLEDGE.md、self-improvement.md 在 buildSystemPrompt() 中每次读取
- **适用场景**: 需要无重启更新的配置

## §4 接口封装

### HTTP 请求封装
- **主流模式**: 单函数导出（每个 API 一个函数）
- **示例**: tools/queryEms.ts 导出 getHomePage()、getBmsYx()、getPcsYc() 等
- **比例**: 100%
- **适用场景**: 所有 EMS 后端 API 调用

### 参数传递
- **主流模式**: 对象参数（可选参数场景）+ 位置参数（必选参数场景）
- **示例**:
  - `getHistoryAlarms({ startTime, endTime })` - 对象参数
  - `getDcdcYc(index)` - 位置参数
- **适用场景**: 根据参数数量和可选性选择

### 响应解构
- **主流模式**: 在调用方解构
- **示例**: `const [homePage, bmsYx, pcsYc, pcsYx] = await Promise.all([...])`
- **适用场景**: 需要并行调用多个 API 时

### 错误处理
- **主流模式**: 调用方 try-catch + 日志记录
- **示例**: processAlarm() 中 try-catch 捕获所有异常，记录日志并通知运维
- **适用场景**: 顶层业务逻辑

## §5 错误与反馈

### 统一拦截
- **主流模式**: 顶层 try-catch + process 事件监听
- **示例**:
  - processAlarm() 中 try-catch 捕获告警处理异常
  - process.on('uncaughtException') 捕获未处理异常
  - process.on('unhandledRejection') 捕获未处理 Promise 拒绝
- **适用场景**: 主流程和全局异常

### 业务 catch 频度
- **主流模式**: 低频（仅在顶层和关键边界）
- **示例**: 
  - processAlarm() 顶层 catch
  - LLMClient.call() 内部 catch（API 调用失败）
  - 工具函数内部不 catch，由调用方处理
- **适用场景**: 需要降级或通知的场景

### 反馈渠道
- **主流模式**: 结构化日志 + 通知（邮件/钉钉）
- **示例**:
  - logger.info/warn/error() 记录所有关键操作
  - notifyOperator() 发送告警处理结果
- **适用场景**: 所有业务操作

### 兜底策略
- **主流模式**: 降级返回 + 人工介入提示
- **示例**:
  - Token 超限 → 降级返回部分分析结果
  - LLM API 失败 → 返回错误信息并通知运维
  - 未知故障类型 → 返回"请人工判断"
- **适用场景**: 无法自动恢复的异常

## §6 TypeScript 类型

### 类型定义位置
- **主流模式**: 集中在 types/index.ts
- **比例**: 100%
- **适用场景**: 跨模块共享的类型

### 类型导入
- **主流模式**: `import type { Alarm } from '../types/index.js'`
- **比例**: 100%
- **适用场景**: 仅类型导入（不导入值）

### any 使用
- **主流模式**: 极少使用，仅在动态数据场景
- **示例**: `realtime: any`（EMS 返回的动态字段）
- **偏离记录**: src/runtime/agentLoop.ts:35 - realtime/history/violations 使用 any（原因：EMS 数据结构动态）

### 类型断言
- **主流模式**: `as Error` 用于 catch 块
- **示例**: `(err as Error).message`
- **适用场景**: catch 块中的 unknown 类型

## §7 导入与模块

### 导入顺序
- **主流模式**: 外部依赖 → 内部模块（按层级）
- **示例**:
  ```typescript
  import 'dotenv/config';
  import cron from 'node-cron';
  import { Heartbeat } from './gateway/heartbeat.js';
  import { AlarmQueue } from './gateway/alarmQueue.js';
  import { logger } from './utils/logger.js';
  ```
- **适用场景**: 所有文件

### 文件扩展名
- **主流模式**: 导入时必须加 .js 扩展名（ESM 要求）
- **示例**: `import { logger } from './utils/logger.js'`
- **比例**: 100%
- **适用场景**: 所有相对路径导入

### 默认导出 vs 命名导出
- **主流模式**: 命名导出（95%）
- **偏离记录**: 
  - better-sqlite3 使用默认导出（外部库）
  - node-cron 使用默认导出（外部库）
- **适用场景**: 优先使用命名导出，除非外部库要求
